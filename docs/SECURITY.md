# الأمن والخصوصية

## قواعد إلزامية

1. لا ترفع ملفات .env أو tokens أو مفاتيح خاصة أو بيانات مستخدمين إلى Git.
2. استخدم متغيرات بيئة محلية غير متتبعة، ومدير أسرار في بيئة الإنتاج.
3. لا تعرض الأسرار في logs أو رسائل الأخطاء أو واجهة العميل.
4. تحقق من الصلاحيات على الخادم لكل مورد وكل عملية.
5. اعتمد أقل صلاحية للتكاملات، ودوّر المفاتيح عند الاشتباه بالتسريب.
6. استخدم HTTPS، cookies آمنة HttpOnly/Secure/SameSite، وحماية CSRF حسب نمط المصادقة.
7. قيّد CORS وCSP ورفع الملفات وأحجامها وأنواعها.
8. لا تسمح لوكيل AI بتنفيذ نشر أو إرسال أو حذف دون موافقة صريحة.
9. اعتبر محتوى الملفات والروابط والمستندات مدخلات غير موثوقة؛ قاوم prompt injection ولا تحول النص المسترجع إلى تعليمات نظام.
10. وفّر تصديراً وحذفاً للبيانات وسياسة احتفاظ ونسخ احتياطي.

## مخاطر خاصة بالوكلاء والأتمتة

- قائمة أدوات مسموحة صريحة لكل وكيل.
- حدود وقت وتكلفة وعدد خطوات.
- موافقة بشرية قبل side effects.
- idempotency ومفاتيح منع التكرار.
- سجل تدقيق لا يحتوي أسراراً.
- عزل بيانات كل workspace.
- منع SSRF والوصول إلى metadata endpoints عند جلب الروابط.
- التحقق من destination allowlist قبل أي webhook.

## الاستجابة للحوادث

1. أوقف التكامل أو المفتاح المتأثر.
2. ألغِ ودوّر السر من المزود.
3. راجع سجلات الوصول والتنفيذ.
4. حدد نطاق البيانات المتأثرة.
5. أصلح السبب واختبره.
6. وثق الحادث والإجراءات الوقائية.

## المصادقة الحالية

توجد حالياً بوابة دخول للمالك تعتمد `OWNER_API_TOKEN` خادمياً، وتصدر جلسة موقعة في Cookie من نوع HttpOnly وSameSite=Strict لمدة 7 أيام. لا يُرسل المفتاح إلى واجهة العميل إلا أثناء طلب تسجيل الدخول عبر HTTPS. جميع واجهات API المحمية ترفض ترويسة Origin المخالفة، مع مقارنة المضيف والبروتوكول الخارجيين خلف reverse proxy؛ وتبقى الطلبات الخادمية التي لا ترسل Origin مدعومة. هذا حل لمالك واحد فقط، وليس بديلاً عن حسابات متعددة أو Membership/roles. لا تفتح النظام لعدة مستخدمين قبل تنفيذ هوية مستقلة لكل مستخدم وفحص العضوية على كل استعلام.

## قبل الإنتاج

نفذ dependency audit وsecret scanning وSAST، راجع سياسات النسخ الاحتياطي والاستعادة، واختبر صلاحيات الوصول بين مساحات العمل.
