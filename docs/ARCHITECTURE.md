# المعمارية التقنية

## الحالة الفعلية

المستودع يحتوي تطبيق Next.js قائمًا، مخطط Prisma لـ PostgreSQL، وواجهات API أولية. الوثيقة تصف ما هو موجود وما هو مستقبلي؛ لا تعتبر المكونات المستقبلية منفذة.

## القرار المعماري

اعتماد **Modular Monolith** في المرحلة الحالية، وليس microservices. هذا يقلل كلفة التشغيل ويتيح فصل الوحدات منطقياً داخل تطبيق واحد. لا تُفصل خدمة مستقلة إلا عند وجود حمل أو حدود ملكية أو متطلبات تشغيلية تبرر ذلك.

لا يعتمد المشروع حالياً على Postiz. المنتج أوسع من جدولة المنشورات، ولم يُجرَ بعد تقييم تقني/ترخيصي يبرر تبني Postiz أو دمج أجزاء منه.

## حدود الوحدات

- identity: الملف المهني، الأهداف، العلامة، والأصول.
- content: الأفكار والمسودات والنسخ الخاصة بالقنوات والموافقات.
- projects: المشاريع والمهام والاعتماديات والنشاط.
- knowledge: المصادر والملاحظات والفهرسة والاسترجاع.
- automations: التعريفات والمشغلات ومحاولات التشغيل والموافقات.
- ai: مزودون موحدون ووكلاء متخصصون واستدعاءات قابلة للتدقيق.
- integrations: اتصالات المنصات وإدارة أسرارها.
- analytics: مؤشرات الاستخدام والتقدم والأداء.
- audit: سجل العمليات الحساسة.

بعض هذه الحدود موثق فقط ولم تُنشأ وحداته البرمجية بعد. الموجود في Prisma حالياً هو User وWorkspace وMembership وProject وTask وKnowledgeItem وContentItem وAuditEvent.

## طبقات التطبيق المستهدفة

1. **Presentation:** صفحات ومكونات عربية RTL ومتاحة.
2. **Application:** حالات الاستخدام، التحقق من المدخلات، وسياسات الصلاحيات.
3. **Domain:** الكيانات وقواعد العمل والأحداث.
4. **Infrastructure:** PostgreSQL والتخزين والبريد ومزودات الذكاء الاصطناعي والمنصات.
5. **Workers:** المهام الطويلة والأتمتة خارج طلبات الويب.

لا تزال بعض المسارات الحالية تنفذ الوصول إلى Prisma مباشرة من Route Handlers؛ استخراج حالات الاستخدام وحدود المجال خطوة لاحقة قبل توسيع عدد الوحدات.

## تدفق API الحالي

1. التحقق من Bearer owner token على الخادم.
2. قراءة JSON مع التحقق من Content-Type وحجم الجسم.
3. التحقق من payload عبر Zod.
4. التحقق من وجود Workspace أو Project المرتبط عند الحاجة.
5. تنفيذ الكتابة وسجل AuditEvent في معاملة Prisma واحدة.
6. إعادة استجابة JSON.

مفتاح المالك آلية تأسيسية مؤقتة، وليس بديلاً عن حسابات المستخدمين والجلسات وRBAC. لا تعرض هذه الواجهات مباشرة لمستخدمين غير موثوقين.

## الاعتمادية المطلوبة قبل الإنتاج

- معاملات قاعدة البيانات مع حدود زمنية ومراقبة.
- rate limiting على مستوى المستخدم/المفتاح والمسار.
- pagination بمؤشر cursor عند نمو البيانات.
- idempotency للعمليات التي قد تتكرر.
- queue موثوقة ومحاولات محدودة مع backoff.
- transactional outbox عند ربط المعاملات بأحداث خارجية.
- مراقبة أخطاء وتنبيهات وhealth/readiness حقيقي.
- نسخ احتياطي واختبار استعادة دوري.
- عزل workspace مفروض في طبقة الخدمة والاستعلام وليس الواجهة فقط.

## نقاط لم تُحسم

اختيار مزود المصادقة، Queue، Object Storage، AI Provider، الاستضافة، ومزودات التكامل. يجب توثيق كل اختيار جديد في ADR قبل أن يصبح اعتماداً أساسياً.
