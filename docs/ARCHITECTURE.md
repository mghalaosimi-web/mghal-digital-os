# المعمارية التقنية

## الحالة الفعلية

المستودع يحتوي حالياً على تطبيق Next.js 16 باستخدام App Router وReact 19 وTypeScript، وواجهة عربية RTL أولية، ومخطط Prisma يستهدف PostgreSQL، ومسارات API أولية للمساحات والمشاريع والمهام والمعرفة والمحتوى، وحراسة بمفتاح مالك خادمي وسجل تدقيق. هذه ليست بعد منظومة إنتاجية مكتملة.

## التوجه المعماري

اعتماد **Modular Monolith** في البداية بدلاً من microservices. هذا يقلل كلفة التشغيل ويُبقي حدود الوحدات واضحة، مع إمكانية فصل الخدمات عند وجود حاجة مثبتة.

## الطبقات المستهدفة

1. **Presentation:** واجهة عربية RTL، صفحات ولوحات ومكونات.
2. **Application:** حالات الاستخدام، التحقق من المدخلات، وسياسات الصلاحيات.
3. **Domain:** الكيانات وقواعد العمل والأحداث.
4. **Infrastructure:** قاعدة البيانات، التخزين، البريد، مزودات الذكاء الاصطناعي، ومنصات النشر.
5. **Workers:** تنفيذ المهام الطويلة والأتمتة خارج طلبات الويب، مع queue وسجل محاولات.

كل وحدة تملك منطقها وواجهات خدماتها؛ يمنع الاستيراد العشوائي للتفاصيل الداخلية بين الوحدات.

## المكدس الحالي والمستهدف

- **منفذ:** Next.js App Router وReact وTypeScript.
- **منفذ على مستوى المخطط:** PostgreSQL وPrisma ORM.
- **منفذ:** Zod للتحقق من payload في مسارات API الحالية.
- **منفذ جزئياً:** حراسة API بمفتاح مالك خادمي واحد؛ ليست مصادقة مستخدمين.
- **مستهدف لاحقاً:** مزود مصادقة موثوق أو جلسات آمنة، Redis/Queue، object storage، ومزود AI عبر واجهة موحدة.

## تدفق طلب API الحالي

1. التحقق من ترويسة Bearer بمفتاح `OWNER_API_TOKEN` على الخادم.
2. التحقق من المدخلات باستخدام Zod.
3. التحقق من وجود workspace أو project المرتبط حيث يلزم.
4. تنفيذ عملية Prisma.
5. تسجيل حدث تدقيق في العمليات المدعومة.
6. إعادة استجابة JSON.

**قيد أمني جوهري:** لا توجد حالياً هوية مستخدم موثقة أو فحوص Membership/role على مستوى كل مورد. لذلك لا يُعد المفتاح الحالي بديلاً عن المصادقة والتفويض، ويجب عدم إتاحة API لمستخدمين غير موثوقين. كما أن إنشاء المورد وسجل التدقيق ليس مضموناً في معاملة ذرية في كل المسارات الحالية؛ يجب توحيد ذلك قبل الاعتماد الإنتاجي.

## تدفق الإنتاج المستهدف

1. المصادقة والتحقق من الجلسة.
2. استخراج workspace من سياق موثوق والتحقق من العضوية والصلاحية على المورد.
3. التحقق من payload.
4. تنفيذ use case داخل معاملة عند الحاجة.
5. حفظ سجل التدقيق في المعاملة نفسها.
6. إعادة استجابة لا تكشف بيانات حساسة.
7. الأعمال الطويلة تنشر job بمعرف idempotency وتنفذ في worker.

## مبادئ الاعتمادية

- timeouts لكل اتصال خارجي.
- retry محدود مع exponential backoff وjitter.
- circuit breaker للتكاملات المتعثرة عند الحاجة.
- idempotency للعمليات التي قد تتكرر.
- transactional outbox عند ربط المعاملات بأحداث خارجية.
- pagination cursor للبيانات الكبيرة.
- فصل liveness عن readiness وفحص اتصال قاعدة البيانات فعلياً.
- مراقبة الأخطاء والتنبيه والنسخ الاحتياطي واختبار الاستعادة.

## القرارات غير المحسومة

المصادقة، queue، التخزين، مزود الذكاء الاصطناعي، واستضافة workers. توثق هذه القرارات في ADR قبل إدخال اعتماد تقني يصعب تغييره.
